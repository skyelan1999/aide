# CAD SHX font recovery follow-up

This follow-up extends the [font fidelity work](2026-11-15-cad-font-fidelity.md) from main `e8c47360`. The user requested another search for source SHX files and a complete archive retest. Previously existing source changes, sessions, plugin settings and drawing originals remain outside the change scope.

## Font provenance and interpretation

The local application, Downloads, workspace, Documents, Desktop and font-directory search found no CAD SHX files. The supplied ZIP and its nested RAR archives previously contained no fonts. The [TSSD vendor download](https://www.tsz.com.cn/downprod/detail.action?id=C190000000000851) and [ZWCAD Taiwan old font-pack link](https://www.zwcad.com.tw/560) were checked; their linked font downloads returned HTTP 404. No guessed filenames are treated as recovered fonts.

Five regular fonts (`txt`, `isocp`, `romans`, `simplex`, `complex`) and two Chinese Big Fonts (`gbcbig`, `hztxt`) were located in attributable public resources. `complex`, `gbcbig` and `hztxt` come from the [MxCAD developer distribution](https://github.com/mxcad/mxcad/tree/main/dist/fonts). The other four come from the [stroke-font archive and documented provenance](https://github.com/golanlevin/p5-single-line-font-resources/tree/main/autocad_sxh_fonts). Every selected file has a private receipt recording source repository, immutable commit, path, size, internal signature and SHA-256. One MxCAD file named `txt.shx` internally identifies a TSSD English face; it was rejected as a TXT match, and the independently archived internally identified TXT file was used instead.

These are same-name font versions with inspected internal identifiers, not proof that their bytes equal the original author's installation. Font binaries remain in the local private font profile; they are not committed or embedded into a public image. Do not rename fallback files to hide missing source fonts. `hzfs`, `hmhz`, equipment-specific fonts and renamed variants remain unavailable unless independently found and verified.

## Implementation

The [ezdxf font documentation](https://ezdxf.readthedocs.io/en/stable/tools/fonts.html) describes regular shape-font support; its current parser rejects Big Fonts. A bounded local adapter now reads the indexed regular Big Font container and uses the existing stroke interpreter for vector commands. It preserves code-page character IDs, native glyph endpoints and subshape IDs. Chinese `gbcbig` and `hztxt` records use GBK mapping. A zero-height Big Font inherits the paired primary stroke font's native cap-height units; positive-height fonts retain their own units. The adapter does not claim support for arbitrary CJK code pages or [extended Big Font primitive placement](https://help.autodesk.com/cloudhelp/2026/ENU/AutoCAD-MAC-Customization/files/GUID-00ED0CC6-A4BE-4591-93FA-598CC40AA43D.htm).

Directory bounds, lead ranges, record spans, command counts, zero divisors, subshape cycles, depth and expanded command work are checked. Unsupported files retain explicit fallback status. The existing 32-file / 32-MiB-per-file / 128-MiB-profile limits and CAD request budgets remain unchanged. Primary/big-font pairs have isolated cached identities, so styles sharing a primary font cannot borrow another style's big font. ASCII stays in the primary face; covered CJK glyphs use the paired Big Font; uncovered glyphs retain the existing checked fallback path. Measurement and drawing use the same runs and advances.

The API additionally reports matched/unavailable Big Font declarations and distinct Big Font glyph selections. The existing viewer match/substitute total and tooltip now include Big Font declarations. These counters supplement primary-face counts: a matched primary face does not imply its declared Big Font is available. Extensionless declarations can match their actual `.shx` files; requested family aliases are tried before conflicting extended-family hints.
