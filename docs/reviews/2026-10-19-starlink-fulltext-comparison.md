# 同一目录：StarLink 与全文搜索定位原文实测

实测日期：2026-10-19。Aide `7774f424`，StarLink `fbaa170`（0.1.2）。本轮仅测量、记录；没有修改产品、调用付费模型或发布。

## 结果

同一物理目录 `aide/docs`，1,199 个文件，36,980,671 字节。当前快照只有 517 个文件节点（43.1%），标记 stale/truncated。8 条人工编写的大意描述，每条先按原始描述字面查询，再使用事先固定的相同关键词重试；每阶段交替顺序重复 9 次。搜索阶段均不知道目标文件名，找到候选后读取源文件核验原文与行号。

| 全文搜索方式 | 星图两次查询及原文读取 P50 | 全文搜索两次查询及原文读取 P50 | 星图相对速度 |
| --- | ---: | ---: | ---: |
| rg 输出匹配行 JSON | 46.1 ms | 69.7 ms | 1.51 倍 |
| rg 先列文件名，再读原文过滤 | 43.4 ms | 83.3 ms | 1.92 倍 |

仅关键词阶段：两批星图 P50 为 29.4 / 22.0 ms，全文搜索为 39.3 / 48.2 ms。上表包含首次大意字面查询的失败尝试，但不包含提炼关键词的模型/人工时间。原始描述字面查询两边均 0/8，提炼关键词后两边均 8/8。StarLink 代码是字符串匹配，本轮不证明语义理解。

这 8 条正例只支持本机工具链约 1.5–1.9 倍的观察，不能称为整体 AI 查找快十倍。8 个案例分别取 9 个样本后汇总 P50（共 72 个同权样本）。不把漏检的短耗时计入加速比。

## 方法与限制

- StarLink 使用运行中 Aide 容器内已安装插件的实际 handler、真实 HTTPS 身份检查与增量接口；没有重放假服务。排除了 Go 工具调度、宿主 IPC 和模型往返。全文用 macOS 的真实 ripgrep，计入进程启动及结果解析。两边读同一物理目录，但运行环境不同，不能当作相同硬件路径下的纯检索引擎比较。
- 两边按整文件关键词 AND；所有候选原文都读取。目标文件与原文锚点仅用于独立核验，不传入搜索接口。自动核验不等价于真实 AI 从候选中挑选、理解和回答所需的耗时。
- StarLink 用来源区域和通用 docs 查询词限制范围，结果再按 docs/ 过滤，最多 100 项；所有样本记录实际是否触发结果上限。较少候选部分来自较低覆盖率，不能归结为更好的排序。
- 第一版全文基线 rg --json 输出行并聚合，第二版 rg -l 只列第一关键词文件，读取候选后过滤其余词。两种基线均报告，没有只选较慢的一种。
- 磁盘/系统缓存为热态。三次新插件进程首次查询分别观察到 144、211、885 ms，含首次快照加载；样本太少，不计算冷态 P50。每批语料的 SHA-256 在测试结束时逐文件核对未变。
- 8 条描述为人工设计，关键词人工预置；不代表真实用户查询分布，没有测出 AI 总体节省时间，也不能推算更大目录的速度。

原始测量、版本、查询、原文证据与逐次耗时见[JSON 记录](2026-10-19-starlink-fulltext-comparison.json)。私有完整清单、脚本与原始样本位于 StarLink 的 `.agent-state/search-comparison*`，不发布用户快照。
