## Current pinned source trace

The issue originally cited an older OpenJPEG commit. This review instead fetched [`jp2.c` at the current core pin `8314119b067c0fc77834731168daaebd379fdb12`](https://github.com/uclouvain/openjpeg/blob/8314119b067c0fc77834731168daaebd379fdb12/src/lib/openjp2/jp2.c) using the GitHub connector. Its Git blob is `3d16d1075fe80651f439f7f9e2e089b99513bc53`; verified pristine file SHA-256 is `45211ee54d24e05f857acc960712fc3acd1655963e6ae12062a2de1075a6777e`. The existing native patch did not modify this file.

- The top-level handler table maps JP2H to `opj_jp2_read_jp2h`; the child table contains IHDR/COLR/BPCC/PCLR/CMAP/CDEF, with no JP2H handler.
- `opj_jp2_read_header_procedure` (2288–2378) reads and dispatches recognized top-level boxes without rejecting an existing header state. Handler failure frees its temporary box buffer and returns false. The procedure is also used for end-header reading.
- `opj_jp2_read_jp2h` (2691–2762) checks FTYP, resets child state, parses children and finally sets `JP2_STATE_HEADER` and `has_jp2h`. It previously had no duplicate guard; an unknown child, including JP2H, was skipped.
- `opj_jp2_read_header` checks the presence of JP2H/IHDR before invoking the J2K header reader. Presence alone does not enforce uniqueness.

[ITU-T T.800 (11/2015), I.5.3](https://www.itu.int/rec/dologin_pub.asp?id=T-REC-T.800-201511-S%21%21PDF-E&lang=e&type=items) requires a single JP2 Header, at the same level as the signature and file type boxes, after FTYP and before the codestream. The static trace confirms the duplicate-header gap remains in the current core pin. This finding establishes container acceptance behavior, not memory corruption, a crash or changed pixels.

## Change

The native patch adds two error returns in `opj_jp2_read_jp2h`: reject `has_jp2h` before resetting child state; reject a direct JP2H child before handler dispatch. Existing successful-header state is reused; no new allocation, ABI change or recursive parser is introduced. Missing-header detection remains upstream. Unknown superboxes remain opaque, so this is not a claim of complete recursive JP2 conformance.

The native patch SHA-256 pin is now `d83f7e323e9354911d1b7e7e228396ed53acce1137e17494fcc3c19f945fa9cc`. The core commit, archive digest, wrapper patch and compiler pin are unchanged. The existing generated decoder, provenance and worker intentionally retain their previous bytes and identities: this handoff does **not** make the added C checks active in the shipped decoder.
