# 普通 SIP 来电断线与历史开场

用户明确要求：接通后“先说一句根据历史推演的引导话”，避免固定自报名字；查询工具后可以继续对话。保留原有待审事项，不批准、拒绝、恢复或修改它们。本次只做本地构建，未推送或发布。

## 已确认与修复

实际普通话机来电在 `assistant_work` 执行约 24 秒后，服务商返回 `invalid_request_error`，消息为 `Unknown function call id`。原事件消费循环同步等待 helper，无法及时处理期间到来的 VAD、取消和新轮次，随后会向已失效编号写回结果。现改为有界异步执行，在新语音轮次取消尚未完成的 helper、丢弃过期结果；不重放查询、不重连付费模型。精确指向本连接已发送输出的失效编号错误只恢复一次，未知编号、账户或额度问题不会被吞掉。

原历史开场策略仍在 `nativeOpeningInstructions`，但普通 Qwen 来电没有触发。现在通过已鉴权来电票据，在接听前生成一句有近期话题依据的开场，并用已配置朗读引擎合成中文音频，接通即播放。生成不提供工具，不派发任务，也不执行历史内容。重复请求同一票据使用已有文本；开场作为宿主参考上下文随实时会话刷新保留，便于用户说“继续”。原 OpenAI 原生开场和已验收的回拨报告流程保留。

服务商 Function Calling 字段与返回顺序已核对[官方文档](https://www.alibabacloud.com/help/en/model-studio/qwen-function-calling)。本文的断线判断依据本机实际错误及离线重现，物理复测另列。

- 原 35 项待审编号集合未变，其所在 24 个会话文件哈希均未变。

首轮物理电话：接通时准备了 134400 字节开场 PCM，约四分钟内有 23 条用户转写、22 次模型响应、6 次 `assistant_work`；未再出现原来的失效调用编号错误，但最终为笼统的客户端读错误。没有将其计为全部通过，听感仍需用户确认。

随后核查发现：电话 helper 清空历史，丢失地点和日期接续；天气事实缺少实时回执约束；开场的三条候选可能全被 Hello／哦挤占；会话检索调用 `sessionBodiesLocked`，在全局锁内解码全部冷历史，存在阻塞语音心跳的路径。后续版本保留本通电话有限用户前文，过滤纯应答，要求本轮 forecast 插件回执并按工具结果朗读。电话检索改为目录搜索，显式指定会话的冷加载移到锁外，普通非电话检索保留。新增的关闭日志有安全代码和固定超时分类，最后一次断开的精确原因仍需新日志确认，未将此推断当作已证实的唯一原因。
