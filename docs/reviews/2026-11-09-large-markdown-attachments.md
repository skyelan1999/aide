# 大 Markdown 附件发送修复

任务 `large-markdown-attachment-20261109`；[集中跟踪 #836](https://github.com/skyelan1999/aide/issues/836)。用户报告附加 1.8 MB Markdown 后发送按钮变灰。基线为 `60485163`。

## 原因与实现

此前文本附件全文进入上下文。发送预览检测到超过所选模型窗口后禁用发送按钮；后端也会拒绝同样的超限请求。直接移除按钮限制不能扩大上游模型容量。

现在 `.md`、`.markdown`、`.mdown` 在一个请求内共享 16 KiB 的全文内联预算。可容纳的小文档继续全文附加并记录准确版本；更大或累计超预算的文档作为明确标记的文件引用附加，附带相对路径、来源、总字节数、行数、SHA-256、最多 768 字节的 UTF-8 开头节选及 `read_file` 字节读取示例。全文留在原文件，节选不表示已经读完，也不产生完整文件覆盖基线。AI 可从任意字节位置读取，按返回的 byteEnd 继续；读取范围和后续文件修改仍走既有版本规则。

本地工作区与本地引用使用流式全文件校验/哈希，只保留有限窗口。SSH 工作区复用现有流式读取；其他引用传输保留各自的传输预算。显式来源 Markdown 的 `read_file` 增加字节窗口，不改变旧的非字节参数路径。引用根使用正确的 source ID；工作区附件不会因为携带无关 source 字段而被导向另一来源。

预览、开始任务和重试共用同一个附件构建器。没有取消模型容量检查、八附件数量规则、非 Markdown 文本处理预算、来源可见性、路径/二进制检查或文件版本校验；本次解决的是大 Markdown 全文内联引起的发送阻塞。

## 旧版实测复现

在现有本地 Aide 创建独立验收会话 #95，通过正常文件 API 准备 1,887,424 字节的纯合成 Markdown，并在实际 Aide 文件面板附加到草稿。

- API 预览：输入估算 387,758，输出预留 8,192，总计 395,950，窗口 65,536，overLimit=true。
- 实际页面：输入估算 389,405，总计 397,597，发送按钮 disabled。界面参数包含草稿当前选项，数值与独立 API 请求略有不同；两者都确认全文超过窗口。
- 测试只使用合成内容，没有上传或发送用户原文件。

## 修复后验收

使用同一个原生 Aide 页面、同一个合成附件重新验证：

- API 预览：输入估算 10,555、总计 18,747、窗口 65,536，overLimit=false；附件上下文仅 1,614 字节、约 314 tokens。
- 页面恢复连接后自动重新计算，草稿和附件保留，不需要解锁或手动重附加。使用正常英文测试指令时页面显示输入估算 12,234、总计 20,426 / 65,536，发送按钮可用。
- 从实际界面点击发送，#95 成功创建任务并完成。模型第一次只读取末尾 24 字节并错误地把这个行中片段当成完整末行；不能把这一答复当成正确解析。补充精确范围后，模型调用 read_file(byteOffset=1887168, byteLimit=256)，返回完整末行，界面显示正确值 `SKY-MARKDOWN-TAIL-20261109`。
- 两次工具读取均返回完整文件 SHA-256 `193e02efa6916b493bc99ad9fe59069922370d21856d9d0a0f592e44f6107dc4`，与原始合成数据一致；文件没有被修改。已验证上传/附加/预览/实际发送和文件尾读取，未把节选当成全文审阅。
