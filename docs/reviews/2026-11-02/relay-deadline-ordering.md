# 中继截止时间通知顺序

问题：[722](https://github.com/skyelan1999/aide/issues/722)。在 ac3db919 的双 worker 全量 race 中，`TestReferenceRelayUntrustedPayloadAndCancellation/cancel` 返回“中继响应无效或超过上限”，没有保留预期的 `context.DeadlineExceeded`。该场景未接受任何不可信内容；此前单 worker 的通过不能否定此次真实失败。

连接读写期限使用了调用者截止时间，但网络 I/O 可能先醒来，上下文计时器稍后才设置 `ctx.Err()`。现有协议读取将 I/O 失败转成了协议错误，外层仅检查 `ctx.Err()`，因此误分类。修复保留显式取消优先级，同时直接检查已经耗尽的调用者期限；丢弃迟到内容，返回标准截止时间错误。未到期限的成功数据、文件不存在等协议错误以及内部连接预算／证书固定／路径和大小检查不变。

回归通过真实 `relayReadSource` 入口模拟“期限已过、通知未到”的确定性窗口，并检查显式取消优先级；另用实际下载的本地 TLS 代理验证未来期限下的读回和文件不存在错误。原来的 100 ms TLS 取消测试及其严格类型断言保留，不用延长时间或放宽断言掩盖问题。无外部依赖的截止时间与原 Go TLS 用例纳入基本 CI，依赖 Python 的完整代理控制场景留在完整 SDK 验收。

实际验证：三组 race 回归各重复 10 次，30 次全部通过；只移除期限判定的独立旧行为 overlay 在确定性场景明确失败，符合预期。全包 basic 编译、关键回归、vet、35 项 Python CI 合约、文档及差异检查通过。完整旧运行收集全部 24 分片后，只有本项失败：1,511 通过、78 跳过、1 失败。修复与旧逻辑的日志均保留，详见[任务账本](../../tasks/relay-deadline-20261102.json)。正式发行仍须重新形成修复后源码的完整通过收据。没有调用真实模型、外部账户或生产服务。
