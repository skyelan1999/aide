- ARM 复用已通过原生 Safari 验收的 `79a0` 镜像，另行从完整包解压，通过原始 `start.command` 强制本地导入启动。鉴权拒绝、构建身份、CAD、工作坊资源通过；无远程镜像拉取或源码重编译。
- 两个独立会话并发写入五档推理强度，共10次，API与磁盘一致；旧版本写入409且不覆盖，新进程重启后选择与修订号保持一致，全局配置不变。未调用真实模型或向量服务。
- AMD 使用保留的完整基础镜像串行离线构建，实际导入后以普通UID检查25项运行资源和DOCX往返。在 ARM CPU 模拟下运行实际安装的 CAD 转换器，装配位置、颜色、完整曲面、NURBS裁剪、线/点、退化面提示、单位与法线边界通过。此结果不等于 Windows 原生验收；Windows仍由用户负责。
- AMD 包的原始启动器在 ARM Docker 引擎上正确拒绝错误架构，未绕过保护启动容器。
- 源码完整回归收据为 `795dd892bd789561c35ea52ceee89ae990edef3c16017d57ceb702543e5215b8`，127条命令全通过，Go服务器976项注册入口分12组串行运行。当前重新计算指纹与该收据一致；本轮未修改任何构建输入，未重复运行重型全量检查。

## 公开发布失败及后续门禁

在现有 RC2 编辑页选择精确 ARM 包两次：第一次显示“Something went really wrong, and we can’t process that file”，刷新后第二次显示“Upload failed. Delete and try uploading this file again”。没有观察到能够定位原因的HTTP状态，不推断是包损坏、大小限制或网络故障。

公开 GitHub API 仍为27个附件，没有本轮包的唯一有效附件；实际执行候选清单校验返回1：`linux/arm64: no unique uploaded public asset`。AMD和两个说明附件尚未上传。保留了既有附件、原RC2标签与说明，未点击 Update release。原07c双架构默认清单及受控SHA文件逐字节未变；旧默认附件可用性与本轮新包公开状态是两个独立结论。

下一步先解决上传渠道，把上述精确包与README/SHA文件追加到现有Release，独立验证 uploaded、字节数和服务端SHA256。两种架构均通过后才允许更新默认清单、受控SHA与操作文档。默认元数据属于验证指纹输入，修改后必须重新运行精确full和main发布门禁。不得把本轮本地验收或现有默认附件门禁当成新包发布成功。
