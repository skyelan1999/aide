# 启动被多个旧容器阻止

用户另一台 Mac 的日志已确认：镜像与源码指纹一致，跳过编译后在 launcher_data_prepare 退出，因此还没进入浏览器打开逻辑。原检查按工作目录和服务名枚举所有历史容器，多个 Compose 项目或一次性任务共享目录时也会被一并计入。

修复先解析启动目录的 Compose 身份，忽略一次性任务容器，并优先使用当前项目唯一正式容器。未显式配置项目且仅有一个旧正式容器时保留旧版继承方式。同项目仍有多个正式容器，或显式项目没有匹配但存在其他项目时，继续在停止与迁移前拒绝，并显示项目与候选数。不会随意采用最近创建或正在运行的容器。

14 项单测通过（其中选择器包含 9 组正常、一次性、QA、遗留兼容及真实歧义场景）。真实 Docker 演练使用 UUID 隔离项目与合成配置，经 start.command 验证同目录三个候选仍能迁移正确数据；活动任务保护、失败恢复旧容器、8 项受保护内容和权限一致、移除自己的旧测试卷与缓存后的恢复均通过。未使用用户工作区、会话或密钥。完整回归、对应镜像与仓库附件发布仍在进行中，不能把本报告当成发布完成收据。

另一台具体容器列表待用户提供；不声称隔离演练等同于该设备验收。Windows 宿主由用户验收，真实向量调用暂缓。
