# FTPS 星图扫描连接延迟

任务：[ftps-index-latency-20261015](../../tasks/ftps-index-latency-20261015.json)。上一轮实际二进制探针完成了 FTP／FTPS 重启续扫，但 FTPS 每轮约一个文件，本轮针对这条可复现线索排查，不替代原 12 项和浏览器验收。

## 测量与决策

在不发布端口的 internal Docker 网络中使用仓库真实 vsftpd 服务与当前应用依赖，curl 为 Debian 修补版 7.88.1、OpenSSL 3.0.22。FTPS 的目录和正文都验证测试 CA，数据通道使用 TLS。每种协议／目录或正文取四次 curl write-out 结果，数据见[测量记录](ftps-index-latency-timings.json)。trace 显示一次正文请求的 TYPE 命令发送后约 184ms 才读到响应，实际 24 字节正文很快完成。

| FTPS 操作 | 默认参数中位数 | 20ms 探索值 | 最终 50ms |
| --- | ---: | ---: | ---: |
| 列目录 | 205.02ms | 21.27ms | 52.52ms |
| 读小文件 | 232.01ms | 30.33ms | 74.88ms |

curl 的 [Happy Eyeballs 参数](https://curl.se/docs/manpage.html#--happy-eyeballs-timeout-ms)控制连接尝试间隔，默认 200ms；更短间隔允许较早启动后备连接，不强制 IPv4 或关闭 IPv6。本机对照实验中，该值改变与 FTPS 停顿同步变化，支持“当前 curl／FTPS 连接调度参与延迟”的判断；这不是对所有 curl 版本或服务器的缺陷认定，也未证明服务端完全不参与。

最终只给 `knowledgeCurl` 的 FTPS 目录和正文请求加入 `--happy-eyeballs-timeout-ms 50`。保留 TLS 要求、证书验证、协议限制、进程超时、读取字节上限、前后来源／凭据身份校验及 350ms 渐进批次预算。没有通过放大批次等待时间提高吞吐，也不缓存目录以跳过变化检测。50ms 会使双栈网络的后备连接更早竞争，真实 IPv6／用户网络未在本批验收。

## 回归与边界

真实七协议整套 race PASS 13.885 秒，新增索引子项 4.31 秒；其中 FTPS 子项为 2.73 秒，上一版本为 6.82 秒。两个环境的总耗时仅作为此夹具观察，不当作普遍加速比例。既有范围优先、分批发布、磁盘重载、取消保留、完整限定目录、六份不同原文的来源／路径／定位／准确内容哈希继续通过。额外将同一服务改为证书未覆盖的 IPv4 地址，读取被拒绝，未返回正文。原有 loopback FTP／隐式 FTPS 测试保留，待完整回归另记。

所有服务、凭据和文件为一次性夹具，未触及当前用户来源／会话，未进行付费模型调用。既有其他协议子项的模型往返仍为确定性模型夹具。本批不证明用户服务器、大库吞吐、真实 IPv6、物理故障或完整已鉴权浏览器。实际新二进制重启／HTTP 检索、镜像包与 main 门禁随后独立记入任务收据。
