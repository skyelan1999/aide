# 小任务队列与自动补位（2026-11-01）

根据用户“50个小任务、完成一个后拉新任务到坑位”的建议，保留按需临时环境架构，增加批量注册、依赖就绪队列、空闲槽位自动补位、队列分页查询和完成者优先收集。没有固定拆分数量；工作粒度由核心调度决定，1X仍使用普通主工具路径。接口及依赖语义见[设计](../../designs/execution-environments-20261101.md)。

受控验证：一次提交50项，容量5X（主环境加4个子环境）；第一项保持阻塞，其他49项在未进行任何主环境collect之前全部完成，说明释放槽位能自动补待办，不被最慢任务挡住。先收集49个完成者，释放第一项后再收集它，所有私有环境已释放、父项目内容不变。该测试使用受控HTTP模型，不是50项真实Luna耗时样本。

八项队列回归覆盖：50项自动补位及分页、无效整批拒绝、前置取消与独立任务不受阻、向后引用依赖及等待取消、逐项汇入冲突不丢其他结果、真实工具分派及子环境不能递归调度、持久化失败不启动任何项、并发提交与关闭。前六项与现有环境、插件、审批、收集、账本和计时器回归合并运行race，17.696秒通过；后两项race重复3遍通过。命令：`go test -mod=vendor -race ./internal/server -run 'TestExecution(Environment|Scheduler|Collect|WorkQueue)|TestBenchmarkPhaseRecorder' -count=1 -timeout=5m -v`，使用已有golang:1.26-bookworm和已有ARM64 Node；初次不含Node挂载的插件测试失败是环境缺失，补齐同一运行依赖后整组通过。并发关闭测试的首版模拟HTTP服务未释放等待通道，修正模拟服务清理后3遍通过；不是产品关闭耗时样本。go vet通过，过程中修正了此前既存并行重试测试的一处JSON tag转义，原测试单独通过。

真实Luna同20模块工程1X/5X重跑，使用与前轮一致的high参数、参考与隐藏验收、独立工作区和分阶段计时；两会话与长源码审查重叠，后半程还与明确小任务策略实验重叠，属于并发负载样本。1X为250.479秒、自由调度5X为190.376秒，减少24.00%；标准113、隐藏变体226、额外差分1330均全通过。自由调度仍选择4个较大分组，因此这组不能证明小任务队列提速。原始证据在`.agent-state/luna-queue-{1x,5x}-20261101*.json`。

另开一组明确要求独立非集成模块逐项入队的5X策略实验，18个小任务实际入队、最多4项运行，主环境负责两个集成模块和报告。这是显式策略实验，不冒充默认调度自动选择；工作区、验收契约与隐藏检查相同，实验启动更晚且共享上游负载不同，不据单次结果推导稳定倍速。原始证据在`.agent-state/luna-small-queue-5x-20261101*.json`。

18项全部完成、汇入普通提案、收集并释放；主环境通过普通apply API在一次性工作区交付20模块和REPORT，无真实源码写入。补位的逻辑入槽间隔最小0.635ms、中位1.040ms、最大22.376ms（不是首token或插件就绪时间）。子任务实际35.94–69.96秒，累计918.028秒与主任务重叠；子任务活跃窗口240.390秒，不能累加到442.142秒上。时间先后为分发前28.529秒、首分发到最后子任务结束240.394秒、随后收尾173.219秒。

这组更细任务比当轮1X耗时多76.52%，没有速度收益。主环境记录126次read_file、11次update_plan、8次collect_ready及10次指定collect；更多上下文/工具回合与重复读取，并叠加124.472秒主压缩，都是明确观察到的成本。不能把全部差额归因于某一种开销；初始槽位、拆分粒度及上游并发负载也不同。额外差分21个失败来自coupon将最低消费与eligible比较，契约要求subtotal；是候选实现错误，不因通过较小的既定集而称完整正确。其他两组额外差分全通过也不代表总体100%准确率。

因此保留批量队列、自动补位及完成者优先收集，并由调度按启动/上下文开销选择粒度；不强制每模块一项、不强制50项。当前还不能声称默认调度稳定选择最优粒度，或达到分钟级/多倍速目标。后续性能问题应针对重复读取、压缩关键路径及粒度成本，不能仅以槽位占用率作为提速证据。计时分区均无事件缺口，详情在对应-analysis.json；Token不完整包含压缩账单。
