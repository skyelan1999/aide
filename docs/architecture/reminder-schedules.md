# 提醒中心的单次定时执行

消息 → 提醒 → 新建提醒，在「到点操作」选择「执行任务」，填写未来的执行时间、执行指令与目标。默认依然是「仅提醒」。目标可以是小秘，或现有普通会话的编号（例如 12 对应 #12）。时间按浏览器本地时区输入，以 RFC3339 UTC 保存，编辑时还原本地时间。

这是服务端一次性调度，无须浏览器常开；Aide 服务必须在线。20 秒轮询，忙碌会话（包括等待审批、澄清、暂停）及满载执行器等待后续扫描。离线期间到期的 pending 任务会在服务恢复、回到原工作区且目标可用后执行。没有 cron/每日循环或系统唤醒功能。

## 数据与执行路径

沿用版本 1 提醒存储，可选 `execution` 对旧通知提醒无影响。仅手动 API 可以创建/编辑执行授权；模型的 reminder 工具保持原有通知能力，不能自行增加执行授权。输入为：

```json
{
  "title": "调试汇总",
  "dueAt": "2026-10-21T02:00:00Z",
  "notify": "both",
  "execution": {"target":"session", "sessionNumber":12, "prompt":"汇总本会话的调试进展"}
}
```

`target:"xiaomi"` 不需要 sessionNumber。服务端解析并保存不可变 `sessionId`、原始编号与创建工作区 ID，不在触发时重新解析编号；所有列表/创建/修改响应深复制执行记录，避免后台写状态与 JSON 序列化竞争。PUT 的 `execution:null` 明确改回纯通知。重排执行需要用户设置未来时间并保存；这构成新的显式执行授权。修改到期时间会重置该提醒的通知回执。

后台先原子持久化 dispatching 领取记录，再最多并行投递 4 项。普通目标调用原有 startTask，沿用该会话模型、工作区、上下文预算、任务上限和执行审批。上下文标记其为 assistant-origin，不成为人工审批或澄清答案。小秘调用原有 assistant-message，保留模型、会话解锁与转交机制；转交继续携带调度工作区约束，不能因为模型等待期间切换工作区而在另一工作区启动任务。小秘工具循环和 push_to_session 同样检查调度工作区。普通非调度输入的执行语义保持原样。

小秘能够自然回复、追问、查询或转交；成功表示该次小秘请求已处理。使用 dispatch_to_aide 转交且获得运行编号时，提醒跟踪该运行的终态；其他小秘工具的执行详情仍在小秘会话中。`runSessionId` 用于转交结果归属，保持原执行目标 sessionId 不变。

## 状态、取消与故障

执行状态：pending → dispatching → submitted → succeeded / failed；小秘直接回复可以从 dispatching 到 succeeded。提交成功只显示执行中，不能当作运行成功；下一次扫描同步 completed/failed/cancelled。已删除目标或服务重启后的未知投递显示 interrupted，不自动重发。原生运行的暂停、审批、续跑仍由目标会话管理。

待执行项有「取消定时任务」，复用 complete API，提醒标记 completed，执行记录标记 cancelled；删除待执行项也阻止触发。已领取/已提交项禁止编辑、完成或删除，提示到目标会话停止任务，待运行终态同步后再管理。状态与错误显示在提醒卡片，可手动刷新；面板打开且没有编辑表单时每 30 秒更新。

持久化领取失败不投递。领取已保存但回执保存失败时，内存显示 interrupted 并提示核对目标会话；磁盘保留领取记录，重启也不会自动重发。这是至多一次投递：领取与实际投递之间崩溃可能漏执行，需要用户先核对，再显式重新安排，不能承诺 exactly-once。模型未配置、目标失效、解锁失败、校验或启动失败会显示错误，不反复付费重试。

存储跟随原提醒文件的原子写、0700 目录和用户私有数据边界；API 使用现有 bearer/同源路径，不添加公开执行端点。调度不提升沙箱、插件或审批权限，不代答审批。执行指令与提醒正文一样保存在用户私有提醒数据中。

## 验收与交付

见 [验收记录](../reviews/2026-10-20-reminder-schedules/verification.md) 和 [任务账本](../tasks/message-scheduled-targets-20261020.json)。测试只用临时用户数据、本地模拟模型和隔离工作台，不调用真实模型、通知联系人或部署生产服务。运行环境仍需部署本次 Go 服务与静态页面，源码推送不代表 Docker 镜像发布。

回滚前先取消尚未提交的执行提醒，并核对执行中任务。回滚源码不删除提醒存储；旧代码会忽略 execution，按原通知提醒处理，不继续调度。
