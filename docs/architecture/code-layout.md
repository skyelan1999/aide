# 代码目录导航

本文说明源码、运行资源和维护工具分别放在哪里，以及新增代码时应遵循的边界。它是仓库导航，不取代各模块内的 API、数据模型或行为说明。

## 仓库树

```text
.
├── cmd/aide/                 # Go 程序入口，只负责装配和启动
├── internal/server/          # HTTP API、任务执行、存储与服务端能力
│   ├── tts/                  # 可独立使用的 TTS 提供商接口与实现
│   └── web/                  # go:embed 打包的浏览器端源码和静态资源
│       ├── locales/          # 界面翻译
│       ├── themes/           # 主题 token
│       ├── avatars/          # 虚拟形象素材包
│       └── vendor/           # 随应用分发的第三方前端依赖
├── plugins/                  # 按插件能力拆分；每个目录自带实现与说明
├── scripts/                  # 启动、开发、校验和发布自动化入口
│   ├── office/               # Office 文档辅助工具
│   ├── fixtures/             # 仅用于校验的模拟数据与服务
│   │   └── mocks/            # 模拟 LLM、TTS 等外部服务
│   └── git-hooks/            # 仓库 Git hook
├── docker/                   # Docker 构建扩展与运行配置
├── docker-images/            # 离线镜像和容器发行相关材料
├── context/                  # 提供给模型的只读参考资料
├── workspace/                # 本地运行工作区示例/默认目录
└── docs/                     # 用户、开发、架构、设计与发布文档
```

## 按工作入口找代码

| 要处理的内容 | 从这里开始 | 边界说明 |
| --- | --- | --- |
| 程序启动、信号与退出 | `cmd/aide/main.go` | 不在入口中放 HTTP handler 或业务实现。 |
| API、会话、任务、持久化 | `internal/server/` | 当前是单一 Go package；具体文件按能力命名，参见 [`internal/server/README.md`](../../internal/server/README.md)。 |
| 浏览器 UI | `internal/server/web/` | 静态资源通过 Go embed 随服务分发；不要把运行时依赖改成外部文件路径。 |
| 可安装的独立插件 | `plugins/<能力名>/` | 插件之间不直接依赖；共享契约由宿主协议提供。 |
| 启动/开发/发布命令 | `scripts/` | 保持现有入口兼容；专项实现可放入已有的 `office/`、`fixtures/` 等子目录。 |
| 镜像制作与离线运行 | `Dockerfile`、`compose*.yaml`、`docker/`、`docker-images/` | 镜像构建上下文、启动入口和持久化目录属于运行契约，改动时要一起核对。 |
| 流程约定与自动路由 | `AGENTS.md`、`docs/agent/`、`scripts/agent-route.py` | 这是开发协作工具，不是 aide 产品运行时的一部分。 |
| 用户可读说明与设计记录 | `docs/` | 活跃说明按主题归档；已完成历史过程放在 `docs/archive/` 或对应审阅记录。 |

## 新增代码的划分规则

1. **按依赖边界建目录，不按文件类型建空壳目录。** 新目录应能说明一个 package、插件、可执行工具或资源域的所有权。
2. **Go 目录就是 package 边界。** 只有当一个能力能够通过小而明确的导出接口工作、无需访问 `server` 的私有状态时，才从 `internal/server` 提取子 package。否则先按能力命名文件和类型，避免为了树形好看而导出大量内部实现。
3. **前端资源以实际加载边界组织。** 可复用的 UI 模块放在 `web/`，语言、主题、素材等拥有独立生命周期的资源放在对应子目录；修改资源位置时同步检查 embed 与 HTML 加载路径。
4. **测试跟随被测边界。** Go 同 package 测试继续与实现同目录，以覆盖私有逻辑；跨 package 的黑盒验收放在独立测试目录或 `scripts/` 校验入口。
5. **维护脚本按用途归组，但入口稳定。** 新增专项辅助程序优先进入已有用途目录；在被工作流、文档或用户启动器引用的脚本迁移时，保留兼容入口或同步更新全部调用点。
6. **生成物、用户数据和第三方依赖不参与源码归类。** `vendor/`、运行数据、构建结果和素材包应留在各自明确的分发/存储边界。

## 为什么暂时保留服务端单目录

`internal/server` 下多个能力共享 `App`、设置、会话仓储、路由和未导出辅助函数，很多同 package 测试也直接验证这些边界。把这些文件机械移动到子目录会创建新的 Go package，迫使内部实现变成导出 API，或引入反向依赖。当前用职责明确的文件名和下方模块索引浏览；等某个能力有稳定接口和独立生命周期，再以一次可审阅的提取重构建立子 package。
