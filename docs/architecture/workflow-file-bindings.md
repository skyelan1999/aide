# 工作流文件绑定的宿主访问边界

文件绑定节点只允许 `read_file`、`list_files` 和 `write_file`，按节点声明的文件或目录路径与读写权限检查；不能使用未绑定引用来源、命令、MCP 或任意插件工具。当前绑定只支持本地工作区。

工作区的 `os.Root` 约束不能代替节点绑定。例如，`allowed/` 被换成指向同一工作区 `other/` 的链接时，仍可能越过节点范围。因此实际读取和审批写入也必须执行绑定约束。

## 文件与目录打开

宿主按组件从已固定的父目录打开子目录，比较打开前后的 `Lstat` 与已打开目录的身份，拒绝链接、非目录或身份变化。后续操作使用目录句柄，避免重新从可能已被替换的路径定位。

- 普通文本、UTF-16 JSON 规范化、按行读取及 Office 原始字节读取均使用绑定文件打开器；叶节点须为普通文件，并经非阻塞打开与文件身份复核。
- 目录列举保持最多2000项；元数据通过已固定目录的 `Lstat` 快照生成，避免 `DirEntry.Info()` 在目录被改名后重新访问原始字符串路径。
- 临时写入文件与最终替换都相对于已固定的父目录执行；已存在的叶链接或特殊文件会被拒绝，缺失的父目录在审批写入阶段逐级创建。

上述检查允许绑定目录内的普通文件内容更新，不提供文件内容的不可变快照、排他写入或外部进程协调。能够修改工作区的进程仍能修改绑定范围内的内容；模型应将文件内容视为不可信数据。

## 从提案到审批

`write_file` 生成提案，审批后才写入。宿主将当时的绑定约束写入 `Change.noSymlinks`，随提案持久化，并纳入审批载荷指纹。约束不依赖当前节点仍在运行，模型参数不能自行关闭它。

人工审批、记忆审批共用应用路径；版本检查、历史快照读取、实际替换及已应用提案读回使用该约束。混合工作区与文档引用提案中的工作区项也按绑定路径处理。

旧提案没有此字段时，如果其工作区路径命中任务保存的工作流定义中任一可写绑定，审批阶段会保守地按无链接路径处理；节点已经结束也适用。路径无法安全确认时拒绝应用，修复目录后可重试。每个文件仍独立替换，整个多文件提案不是原子事务，部分成功的记录遵循既有应用流程。

实现位于 `professional_workflow_bindings.go`、`workflow_bound_files.go`、`workflow.go`、`files.go` 和 `document_proposals.go`；提案规则也见[插件协议](../plugin-protocol.md)。

## 验证范围

宿主单元测试使用隔离工作区与合成的启用任务：目录替换竞态、提案序列化、当前节点结束后的审批、旧提案与混合文档应用、叶链接、分行 JSON、原始字节及新建目录。测试没有执行商业引擎，也没有修改或绕过运行时签名验证；需要真实签名运行时的集成用例仍按原规则跳过。

完整工作台、商业引擎实际工作流及 Windows/macOS 文件系统验收需在具备对应环境和运行时的环境中另行执行。
