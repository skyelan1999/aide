## 开发流程
1. 保持审批请求/操作本体不变，以 pending shell command、Task.AgentRoot 与当前 Change 列表为唯一摘要来源。
2. 服务端构造可重复确定的执行意图文本及文件目标明细，将其提供给辅助审核模型，并将 shell 相关意图随 pending question 提供给 UI；文件审批 UI 根据当前提案数据构造同义摘要。
3. UI 将意图置于审批按钮之前；命令/路径/内容仍作为原始证据展示，辅助审核仍必须判断原始命令或完整文件提案。
4. 对摘要构造和变更范围加入单元测试，再运行针对性 Go 测试与前端语法/差异检查。

## 依赖条件
- 现有 `Task.AgentRoot` 提供命令工作目录快照。
- `PendingQuestion.command`、`Task.Files` 是同一执行/应用路径消费的原始待审载荷；文件目标经 `proposalDisplayPath` 展示。
- 未应用 Change 才会被 apply 路径写入；现有文件覆盖、远端目标与不确定风险依然按当前逻辑转人工。

## 架构需求
- 增加纯函数生成 shell 与文件提案执行意图/目标信息，避免基于自然语言猜测 shell 实际触及目标。
- shell 意图包含动作、工作目录、无法静态确认的目标/网络/外部副作用提示；原始命令仍传入审核模型和 UI。
- 文件意图只纳入尚未 Applied 的 Change，提供路径、创建/修改判断与文件数，并注明批准会写入这些目标；完整 Change 仍传入审核模型。
- 不将摘要绑定范围替换为批准机制；保持已有 command fingerprint、file fingerprint、持久化先于自动放行/应用以及版本检查。
- 保持旧审批记录兼容；用户界面翻译需同步英文键值。

## 待确认项
- 通过代码验证 PendingQuestion 来源和 AgentRoot 序列化字段；无法静态解析复合命令的实际影响仅作明确提示，不承诺目标归纳完整。
- 验证目标路径文本与服务端 apply 的 Change 顺序/范围一致，尤其是已应用条目及部分应用重试。
- 现有浏览器验收能力是否可用；如无，不虚报 UI 运行时验证。
