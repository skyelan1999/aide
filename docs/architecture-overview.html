二、关键功能 → 实现技术 / 协议 / 算法

功能实现方式为什么这样设计（优势）
流式输出 text/event-stream SSE；后端逐 token 推 delta，前端 rAF 批量 innerHTML，避免每帧全量 markdown 解析 协议比 WebSocket 简单、走 HTTP 自动穿透；rAF 节流让 1000 token/s 也不卡 UI
AI Tool Loop OpenAI function calling 协议；循环 ≤10 轮，工具结果以 role:tool 回灌 协议标准 Chat Completions，任意兼容后端都能接；轮次上限防爆 token 黑洞
写文件双阶段 write_file 只构造提案（JSON files[]），任务进 awaiting_approval；用户点 apply 才逐文件原子替换，带 SHA 哈希比对 安全模型不会静默改你的代码；哈希冲突检测防止覆盖你手动改过的文件
Shell 沙箱执行 bash --norc -c，受限 PATH/HOME，60s ctx 超时，输出 128KB 截断，危险命令前缀黑名单（rm -rf / sudo / git push / pipe-to-sh …）直接拒绝 安全Docker 已 cap_drop [ALL]+no-new-privileges；黑名单拦高危；普通 ls/go test 等只读命令自动跑
运行中插话 vs 排队 Steer 通道即时打断当前 toolLoop；Queue 通道 FIFO 排队，当前轮结束后按序处理；前端 Codex 风格队列条可上移/删除/编辑 体验打断不丢上下文；排队消息用 【你回答过程中用户插话】 包装喂回模型，避免被当成新话题
上下文管理 请求前 context-preview 算预算；接近上限时触发结构化摘要压缩（旧历史 → summary），保留最近 60K 回放窗口 算法不是粗暴截断，是分层摘要；前端实时显示 tokens/64K 进度条
工作区身份绑定 wsID = 模式+主机+路径+revision；旧提案在切换工作区后拒绝应用（R02/R03） 安全防止 A 项目的文件提案被误写到 B 项目
插件系统 DSH/Cordis 形态 module.exports={apply(ctx){ctx.tool(...)}}；Node 宿主加载，handler 结果经 normalizePluginResult 归一化成 tool 消息 协议用户可上传 JS 扩展工具面；但插件是可信代码，不是安全边界
远程工作区 SSH 长连接 + SFTP 批处理；shell 命令通过 ssh target "cd dir && cmd" 执行 兼容本地文件 API 对前端透明，远程/本地同一套 UI
会话持久化 每个会话一个 JSON 文件（/data/session-<id>.json），记录 runs/messages/proposals；启动时全量加载 简单无外部 DB，单文件易备份/导出；SSE 断线后用 GET 会话状态兜底
鉴权 启动时生成一次性 access-token 写 /data/access-token；前端 Bearer 携带；SSE 用 ?access_token= 安全本地工具不需要用户体系；令牌不进前端 localStorage 持久域

三、技术栈与部署

后端

  • Go 1.22+ 标准库 net/http（Go 1.22 method 路由），无框架
  • goroutine 跑每个 run；context.WithCancel 支持取消
  • //go:embed 把整个 web/ 目录编进二进制，单文件分发
  • 测试：标准 testing + httptest + mock_provider.py

前端

  • 原生 ES2020 JS，无 React/Vue；marked v12 渲染 GFM
  • i18n.js 双语（zh-CN/en）；CSS 变量双主题
  • EventSource 订阅 SSE；URL hash 路由 file-view

容器

  • Docker Compose 单容器；Go/Python/Node/Git 工具链内置
  • cap_drop [ALL] + no-new-privileges + pids_limit + mem_limit
  • 端口 127.0.0.1:8097 → 8080，不暴露公网
  • /workspace RW、/context RO、/data 持久卷分别挂载

外部依赖

  • 仅一个：OpenAI 兼容 Chat Completions API（DeepSeek 或本地 vLLM 等）
  • 无 DB、无 Redis、无消息队列、无 OSS
  • 插件宿主需要 Node（容器内已装）

四、设计优势与当前边界

✓ 优势

  • 单二进制 + 单容器：启动一条命令，数据全在 /data，迁移即拷贝卷
  • 写操作可控：AI 只读+自动跑只读命令，写文件必须人点批准，符合"人在回路"
  • 流式体验：SSE + rAF 批量，长回答不卡 UI；运行中可插队可排队
  • 工作区身份隔离：切换项目后旧提案自动失效，不会写错地方
  • 协议开放：模型端是标准 Chat Completions，换模型=改一行 BaseURL

! 边界 / 后续可改

  • run_shell 无 PTY，跑不了 vim/top 等交互命令
  • 危险命令黑名单是前缀匹配，可被绕路；正式版建议加 allowlist 模式
  • 会话 JSON 单文件，会话数上千后启动加载会变慢（未做分页）
  • MCP 仅登记入口，未真正接 MCP 协议
  • 远程 SSH 工作区的 run_shell 自动执行尚未打通
  • 权限管理目前是只读说明面板，还没做 per-user 开关持久化
